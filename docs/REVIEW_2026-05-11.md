# Grid Genius — Senior Design & Code Review

**Date:** 2026-05-11
**Reviewer role:** Senior game designer, UX reviewer, math-puzzle gameplay analyst
**Scope:** Full codebase under `code/src/`, plus `public/puzzles.json` and design docs in `code/docs/`
**Commit reviewed:** working tree at the time of review (see `git log -1` for the exact SHA)

> A note on framing: the brief described the game as "select 3 numbers from the grid… use arithmetic on those 3 numbers." That is **not what the shipped game does**. The shipped mechanic forces selection of numbers in a **straight, contiguous line** (horizontal _or_ vertical), with operators chosen _between_ each pair. The gap between intent and implementation is itself a finding — see §1 and the recommendations in §8.

## 1. Core Gameplay

### Is the objective clear?

Mostly. The on-screen "Make this number" + a giant green pill is unambiguous (`src/components/UI/TargetDisplay.tsx`). The mode selector card even reads "Make the target number." Good.

### Are the rules intuitive?

**No.** Three hidden rules trip new players hard:

1. **You must pick tiles in a contiguous straight line.** Nothing on the board communicates this. `isValidPath` and `isTileValidForNextSelection` (`src/components/GameBoard/ButtonGameBoard.tsx` lines 689–736) silently reject any non-adjacent or bent selection. The only "feedback" is `navigator.vibrate(100)` — fine on a phone, invisible on desktop. A player trying `7` (top-left) and `3` (bottom-right) gets _zero_ visual explanation of why nothing happened.
2. **You must alternate tile → operator → tile.** Lines 250–268. Tap two tiles in a row with no operator between them and you get the same silent rejection. This is a _non-obvious_ state machine.
3. **There is no operator precedence.** `calculateResult` evaluates strictly left-to-right (`src/utils/calculator.ts` lines 4–45). The test file even celebrates it:

```19:22:code/src/utils/calculator.test.ts
   it('evaluates left-to-right with no operator precedence', () => {
     // 2 + 3 * 4 with precedence would be 14; left-to-right gives 20.
     expect(calculateResult(2, '+', 3, '*', 4)).toBe(20);
   });
```

This is the single biggest gameplay/education trap. Any kid who's been taught BODMAS will type `2 + 3 × 4`, see it accepted as `20`, and either be confused or — worse — _unlearn_ operator precedence. The math game is actively miseducating its audience.

### Is the 3-number arithmetic mechanic engaging?

Engaging for a few rounds, then it collapses:

- The "puzzle" reduces to "scan 8 rows/columns of a 4×4 grid, find which one sums to N." On a 3×3 with `tilesCount=2` there are only `3·2 + 2·3 = 12` candidate pairs × 2 operators = 24 attempts. With the target on screen, brute-force visual search beats any reasoning, especially for adults.
- All tile values are in `[1, 9]` (`MIN_NUMBER=1, MAX_NUMBER=9` in `src/constants/game.ts`). For target `12` on an easy board there are dozens of valid `a+b=12` variants — too many trivial solves on most grids.
- The "3 numbers" promise is misleading. There's no real "pick any 3" decision space — you pick _a starting tile, a direction, and operators_ between fixed neighbours. Structurally a much smaller puzzle than the design doc implies.

### Loopholes & confusing cases

- **The "match 0/1" loophole.** Subtraction levels with `targetRange.min = 0` (e.g. `u2-l1`; `u2-l2` used to duplicate it) make `5−5=0` valid. Any same-value pair beats the level. — **Partially addressed:** `u2-l2` is distinct with `min: 1`; **`u2-l1` still allows zero targets.**
- **Negative results are silently inadmissible.** `getAllCombinationsFromConfig` filters with `result >= 0` (`src/utils/gridGenerator.ts` lines 92, 117) — but only during target generation. At play time, `submitSolution` doesn't enforce this; if a player produces a path with a negative intermediate, it just won't equal the target. Means negative numbers as _targets_ are impossible and players are never told why.
- **Hint cheese.** The 💡 button (`findHint`, `ButtonGameBoard.tsx` lines 377–394) is free, unlimited, and reveals the first valid solution in 5 s. Press hint → wait → memorise → tap. No cap, cost, or score penalty. — **Mitigated:** one hint per round + score penalty; hint timeout cleared on unmount (see **Implementation status**).
- **Auto-clear race.** After a correct/incorrect submit, `setTimeout(clearSelection, 2000)` (line 572) fires unconditionally. The player can start a _new_ selection within those 2 s — and have it nuked from under them mid-tap. — **Partially mitigated:** feedback timeout tracked/cleared on unmount; **behaviour** still auto-clears after the delay.
- **Dead retry on wrong answer.** A wrong submission gives "Try Again" then auto-clears your selection. If your answer was off by 1, you have to _rebuild the whole path_ to fix one operator.
- **No "submit" button.** Submission auto-fires when `tiles.length === tilesCount && operators.length === operatorsCount`. A mis-tap on the last operator instantly counts as a wrong submission.

## 2. Puzzle Generation

### Are generated puzzles always solvable?

For random Play mode: **almost always but not provably.** `generateValidGridFromConfig` retries up to 10 times for a grid that has at least `totalRounds` valid combinations (`src/utils/gridGenerator.ts` lines 194–209), then falls back to _whatever the last attempt produced_ with a warning. The store has its own `MAX_INIT_RETRIES = 5` wrapping that. In the worst case a player still sees a board with too few combinations to satisfy 5 rounds — there is an `initError` path that handles this, but it's a "Couldn't start the game" dead-end. The Hard config (`targetRange.max=50`, with `tilesCount=3` and `*`) is exactly the configuration most likely to hit it.

For static puzzles in `public/puzzles.json`: yes, solvable by construction — the build script picks an existing combo and saves it as `optimalSolution`.

### Are puzzles too easy or hard?

**Mostly too easy, with sudden cliffs.**

- **Easy.** 3×3 grid, two adjacent tiles, `+ -` only. 24 candidate moves. Tile values 1–9 keep the answer space in `[2, 18]`. Pattern-matched in a glance.
- **Medium → Hard.** Identical grid size (4×4), identical tiles, identical operator set (`+ - *`), identical `tilesCount=3` and `operatorsCount=2` (`src/constants/game.ts` lines 12–27). The _only_ difference is `targetRange.max` (35 vs 50). Players will not feel a meaningful jump between them.
- **Multiplication cliff.** As soon as `*` joins the available operators, the result space jumps to `≤ 81 × 9 = 729`. The combo filter `result ≤ 50` (hard) prunes most of the interesting `*` solutions — so paradoxically, "Hard mode" has _fewer_ multiplication-heavy puzzles than "Medium" feels.
- **No within-difficulty progression.** Inside a 5-round Classic game, all 5 rounds use the same config. The 3rd target feels like the 1st target.

### Is there difficulty progression?

- **Play mode: no.** Three coarse buckets, two of them near-identical.
- **Learn mode: yes, and it's the strongest part of the design.** `src/constants/levels.ts` ramps one axis at a time (operators → grid size → path length). Excellent design intent. Two real defects:
  - **`u2-l1` and `u2-l2` are byte-for-byte identical** (lines 84–106). Authoring bug. — **Fixed** in code (`u2-l2` distinct; see Implementation status).
  - **`u3-l1` → `u3-l2` bumps two axes at once** (`tilesCount` _and_ `operatorsCount`), violating the file's own authoring guideline. — **Fixed** (single-axis steps).

### Are target numbers well chosen?

- Targets are picked uniformly from all valid combinations (`generateTargetsFromConfig`, lines 134–184). This biases targets toward whatever the random grid happens to produce a lot of. Grids with several 8s and 1s will see targets like 9, 17, 18 over and over.
- **No target diversity guarantee within a session.** Nothing prevents two rounds in the same game from having the same target. Time Attack can repeat the same target on consecutive rounds (line 311).
- **Shuffle is broken.** Both `generateTargetsFromConfig` (lines 158, 163, 176, 183) and Time Attack use `Array.sort(() => Math.random() - 0.5)` — a known-biased shuffle. Use Fisher–Yates (already implemented in `rng.shuffle`). — **`generateTargetsFromConfig` fixed** (`shuffleUniform`). Time Attack still picks a random target index with `Math.random()` (unbiased for a single pick).

### Repeated / trivial solutions

- **No de-dup on `result` within a target set.** The selected combinations can hold three combos all evaluating to 10 from different paths.
- **Trivial 2-tile `a + b` solutions.** When `+` is available, any adjacent pair summing to the target is a hit. Targets like 12 typically have 3+ valid lines on a 3×3 board.
- **The seeded puzzle generator picks the first valid combo from the RNG and calls that "optimal" with no quality criterion** (`buildPuzzle` in `src/utils/puzzleBuilder.ts` lines 70–107). "Optimal" is a polite fiction.
- **`computeRating` clusters at the floor.** Every `easy + addition-only + 2-tile + target≤30` puzzle ends up at `rating: 800` (confirmed in `public/puzzles.json`). The rating field provides essentially zero signal for half the bundle. Calling it "Glicko-style" in the comment is misleading — it's a static formula, not a rating.

## 3. Game Balance

### Scoring

```271:274:code/src/store/gameStore.ts
    const baseScore = 10;
    const difficultyMultiplier = difficulty === 'easy' ? 1 : difficulty === 'medium' ? 1.5 : 2;
    const timeAttackMultiplier = gameMode === 'timeAttack' ? 2 : 1;
    const roundScore = Math.floor(baseScore * difficultyMultiplier * timeAttackMultiplier);
```

That is the entire scoring system. Issues:

- **Flat per-round score.** No time bonus, no streak bonus, no penalty. Solving in 1 s is worth the same as solving in 59 s.
- **Hints are free.** Five hints in Time Attack score the same as five unaided solves.
- **Wrong attempts have no cost in Play mode.** They count toward `wrongAttempts` only in Learn/Daily.
- **Time Attack only doubles score.** A player who solves 20 puzzles vs 5 in the same minute gets a `40 → 200` spread — purely from quantity. No quality factor.
- **The "max score" on `ResultPage` assumes no wrong attempts and no missed rounds**, so the "Outstanding!" thresholds effectively just check that you finished the game (which the page only renders when you did). The judgmental copy is decorative.

### Hints, retries, timers, penalties

- **Hint:** unlimited, instant, free, auto-hides after 5 s. Should cost score, take time, or be limited per round.
- **Retries:** infinite. Wrong submit auto-clears after 2 s.
- **Timer:** purely cosmetic in non-Time-Attack modes. Time Attack uses a 60 s wall clock. No leaderboard, no personal best — timer is cosmetic at the player level once the round ends.
- **Penalties:** none, except a silent `navigator.vibrate(100)` for invalid taps.

### Speed vs thinking

Time Attack rewards speed; Classic and Quick Game reward nothing. There is no "thinking-rewarded" mode that scores _path elegance_ (longer path = more points; mixed operators = bonus). The mode space currently has two real points — "as fast as you can" and "without any pressure" — and nothing in between.

## 4. UX / UI Review

### Board readability

- Tile values look good (`NumberTile.tsx`). Three sizes scale via `min(NNvw, NNpx)` — nice mobile-first thinking.
- **Operator hit targets are tiny.** `w-4 h-12` on small viewports (`OperatorIcon.tsx` line 57) is **16 × 48 px** — narrower than Apple's 44 × 44 minimum and much narrower than Material's 48. Mis-taps on phone, constantly.
- **3 operators stacked between every pair of tiles** when `availableOperators = ['+', '-', '*']`. On a 4×4 with mixed operators that's `4×3×2 = 24` operator buttons, plus 16 tiles. Cognitively dense.

### Are number selections obvious?

- Selected tiles get a clear blue gradient + pulse + numeric badge (1, 2, 3) — **excellent.**
- But there's no "selection ghost" showing _which tiles can be selected next_. The constraint is learned by getting silently rejected.

### Operation input

- Click-an-inline-operator works once you grasp it. The flow "tap tile → tap operator between tiles → tap next tile" is reasonable.
- No visual line drawn between successive tiles — the **path you're building is implicit**.
- Discoverability of "you must alternate" is zero.

### Feedback when correct/wrong

- **Correct:** green pulse, ✓, celebration particles, auto-advance. Particles are nice.
- **Wrong:** red box, ✕, "Try Again." Doesn't say _what_ was wrong. Was it the operator? The tile? `CalculationFeedback.tsx` shows `= 20`, leaving the player to mentally diff. Add: "Your answer was `20`, target is `14`. Off by 6."
- **The neutral-blue case in `CalculationFeedback`** (`isCorrect === undefined`) is unreachable because `checkAnswer` always sets a boolean. Dead code path; delete.

### Mobile / desktop usability

- Desktop: keyboard navigation is **excellent for a hobby project** — roving tabindex, arrow keys, Enter to select, `?` for help, Esc to clear, `Z` for zen. Genuinely above average. Good ARIA labels.
- Mobile: tile sizes are responsive; operators are not. PWA install prompt is in place. Haptics work.
- Layout uses `overflow-hidden` on the root container (`App.tsx` line 56), which **clips content** below the fold on landscape phones with the OS URL bar visible. The `safe-pad` helper exists but doesn't address the root `h-full` + `overflow-hidden` combination.

## 5. Educational Value

### Does it improve arithmetic skills?

Conditionally:

- **Easy Learn levels (Unit 1, addition only):** Yes. Pure addition drill, friendly framing. Solid for ages 5–7.
- **Anything that mixes `*` with `+`/`-`:** **No, and possibly _negative_ educational value**, because the game enforces left-to-right evaluation. `2 + 3 × 4 = 20` in this game; in school it's `14`.
- **Subtraction:** Limited. The same-value-equals-zero trick means kids learn "find two of the same number" instead of doing subtraction.

### Does it encourage reasoning?

Not really. The action space on a 3×3/2-tile board is small enough that visual scanning beats reasoning. On a 4×4/3-tile board with three operators the space is larger, but there are no scaffolds — no notepad, no "try this operation" coaching, no near-miss feedback.

### Are explanations / steps provided?

**No.** This is the single biggest educational miss.

- Wrong-answer feedback shows the expression and the wrong result but doesn't compare to the target.
- The Hint button reveals a complete solution, not a _next step_.
- The end-of-level Result screen shows stars and XP but no recap of which problems were missed or what to practise next.
- There is no in-game tutorial. The `?` help dialog only documents keyboard shortcuts (`ButtonGameBoard.tsx` lines 851–880).

## 6. Replayability

### Does it feel different each round?

Visually yes (new grid). Mechanically **no** — every Easy round is "find an adjacent pair." Every Hard round is "find a row or column of three that lands on the target." Same puzzle template, new digits.

### Modes

You have: **Quick Game, Classic, Time Attack, Learn (25 levels), Daily Puzzle.** Endless and Puzzle modes are scaffolded but disabled (`available: false`). Notably missing:

- **No multiplayer** (called out as Phase 2 in `VISION.md` — fine for now).
- **No leaderboards / personal bests.** The score that motivates Time Attack is forgotten the moment you hit "Back to Menu."
- **No streaks within a single game** (Time Attack tracks `timeAttackRoundsCompleted` but doesn't reward unbroken streaks).
- **No "puzzle of the week" / weekly leaderboard.**
- **No "share my puzzle" / "challenge a friend"** for social retention. You ship a deterministic seeded RNG (`rng.ts`) — you're already 80% of the way there.
- **No theme UI for Play mode.** `puzzleThemes.ts` defines 6 themes; the player never picks one in `GameModeSelector`.

### What would increase retention?

In order of likely impact:

1. **Personal-best tracking + streak protection** (you already store streaks for Daily/Learn — extend to per-mode PBs).
2. **Shareable seeded puzzles** ("`/puzzle/abc123` — beat my time").
3. **Daily streak that's visible everywhere** with a 🔥 freeze risk. The data is there; the UI underuses it.
4. **Puzzle Storm / Puzzle Streak modes** — in `VISION.md` but unbuilt. The highest-retention lichess features; would translate directly.
5. **Near-miss hint instead of full-solution hint.** "You're close — try a different operator in slot 2."

## 7. Technical Review

The engineering is the strongest dimension. Genuinely thoughtful. Specific findings:

### Architecture

- Zustand is appropriate. `gameStore` is large but coherent; persistence (`prefsStore`, `progressStore`) is well-scoped and includes a sensible v1→v2 migration.
- Loading `puzzles.json` lazily with a module-local promise (`puzzleStore.ts`) is good — much better than putting 617 KB into the JS bundle.
- The `FromConfig` / `FromDifficulty` wrapper pair in `gridGenerator.ts` cleanly supports Learn levels without forking the core logic.
- Routing is clear; `HomeShell` + `Outlet` is fine. `App.tsx` is overgrown because it carries wizard state for the Play tab — that state belongs in a small store or context, not in the root component.

### Bugs and fragile logic

1. **Biased shuffle** in `gridGenerator.ts` lines 158, 163, 176, 183, and `gameStore.ts` line 311. `[...a].sort(() => Math.random() - 0.5)` is not a valid shuffle. Use the `rng.shuffle` you already wrote. — **Fixed** in `generateTargetsFromConfig`; see Implementation status.
2. **`generateTargets` uses `Math.random()` even when the rest of the puzzle was built from a seeded RNG.** For Daily Puzzles this doesn't matter (`initializePuzzle` skips target generation), but it will silently break any future seeded Quick Game.
3. **`SUCCESS_DELAY` (`src/constants/game.ts` line 50) is exported but unused.** `submitSolution` hard-codes `AUTO_ADVANCE_DELAY_MS = 1500` and the board uses a separate `setTimeout(..., 2000)` for clearing. Three different magic numbers should be one constant. — **Addressed** (`SUCCESS_DELAY_MS`, `FEEDBACK_CLEAR_DELAY_MS`).
4. **Race in `ButtonGameBoard.checkAnswer`:** the `setTimeout(..., 2000)` doesn't track its handle. If the player navigates away during those 2 s, `clearSelection` and `setShowFeedback(false)` fire on an unmounted component. — **Addressed** (tracked timeout + cleanup).
5. **`submitSolution` auto-advances via `setTimeout` (`gameStore.ts` line 285) but doesn't pause if the player tabs away.** Backgrounded tabs on slow devices can pile up. Use a visibility check, or pause/resume timers.
6. **`feedbackData.isCorrect === undefined` is dead state** — the type allows it, the styling handles it, but `checkAnswer` always passes a boolean. Narrow the type. — **Fixed**.
7. **`isOperatorValidForSelection`** allows selecting an operator whose row/col matches the previous tile but doesn't validate that the operator's _direction_ matches the path so far. Contributes to silent-rejection UX. — **Fixed** (straight-line axis guard).
8. **Time Attack `nextRound` calls `getAllCombinations` _and_ `generateTargets` every round** (`gameStore.ts` lines 307–308) — combinatorial work on every successful tap, 60 times a minute. Fine at 4×4; not fine at 6×6.
9. **`MIN_NUMBER = 1, MAX_NUMBER = 9`** is hardcoded in `gridGenerator.ts` line 19 _and_ `puzzleBuilder.ts` line 45. Two sources of truth.
10. **`tile.selected` is on `Tile` but the store never reads or sets it** — reset on every grid update. Dead field; remove. — **Fixed**.
11. **`computeRating` has a hard floor of 800** that pins ~half the puzzles. Rating is effectively unused signal.
12. **`puzzles.json` is bundled into `public/` and served as a single 617 KB file.** Split by theme/difficulty and lazy-load only the slice you need.
13. **Wizard state lives in `App.tsx` `useState`** (`selectedGameMode`, `selectedDifficulty`). If a Time Attack player refreshes mid-game, the next render hits `<Navigate to="/play" replace />` (`App.tsx` lines 176–178) and you lose the game.
14. **`MAX_INIT_RETRIES = 5` outer × `maxAttempts = 10` inner = 50 attempts** in the worst case. Cap attempts and surface a clearer error earlier.
15. **No CI gate on `puzzles.json` validity** — the validator script exists; verify it's wired into a workflow. A broken bundle ships silently otherwise.

### Performance

- `ButtonGameBoard.tsx` is a 1,100-line component with a lot of inline JSX, framer-motion wrappers, and event handlers. Splits into `<Grid>`, `<Header>`, `<OverlayControls>` will help. The `findValidSolutions` function is a 154-line monolith — extract it.
- On a 5×5 grid with operators, framer-motion animates ~60 elements per render. `MotionConfig reducedMotion="user"` is set (good); verify tiles actually skip springs on slow devices.

## 8. Improvement Roadmap

### Critical fixes (this week)

_See **Implementation status** above for Done / Partial / Open._

1. **Fix the operator-precedence trap.** Either (a) display the expression with **explicit parentheses** as the player builds it — `((7 + 5) × 2)` — and evaluate left-to-right with that visualisation, _or_ (b) implement real precedence in `calculator.ts`. Option (a) is honest and avoids retraining math intuition; (b) is what kids' brains expect. Pick one. The current "left-to-right, hidden from the player" is the worst of both. — **(a) shipped; (b) not.**
2. **Teach the rules.** First-time-player tutorial (3 screens; skippable). Even one animated GIF on the home screen showing "tap → operator → tap" would crush onboarding bounce. — **Done** (tutorial + copy; no GIF).
3. **Fix the shuffle.** Replace every `sort(() => Math.random() - 0.5)` with `rng.shuffle` or Fisher–Yates. — **Done** for target shuffling in `generateTargetsFromConfig`.
4. **De-duplicate `u2-l1` and `u2-l2`.** Distinct configs. — **Done** (also fixed `u3` single-axis ladder).
5. **Show _why_ a wrong answer is wrong.** "Your answer = 20. Target = 14. Difference: +6." Bare minimum. — **Done**.
6. **Visualise the path.** Connecting line/stroke between selected tiles. Highlight next-legal tiles after each selection. — **Done**.
7. **Cap or cost the hint.** 1 hint per round, or −5 score for using it. — **Done** (both).
8. **Track and display personal bests** in Play mode — fastest Quick Game, longest Time Attack streak. — **Done** (those two metrics).
9. **Make operator buttons ≥ 44 px on the long axis.** Currently 16 px wide on mobile. — **Done**.

### High-impact improvements (this month)

1. **Real difficulty progression within a session.** Round 1 of a Classic game should be easier than round 5.
2. **Distinguish Medium from Hard.** Give Hard `tilesCount = 4` or a `5×5` grid or introduce division.
3. **Allow non-straight paths.** Lift the straight-line restriction. Let the player pick any 3 _connected_ (orthogonally adjacent) tiles. The puzzle space explodes; the game becomes the "Genius-style arithmetic puzzle" the design doc describes.
4. **Solution explanations on Result page.** "On round 3 the target was 27. One path: 9 × 3 = 27. Two more paths existed."
5. **Per-theme Daily Puzzle + weekly leaderboards.**
6. **Shareable puzzle URLs.** `/play?seed=abc123` boots a deterministic puzzle. Two-line change with your existing seeded RNG; massive viral upside.
7. **Endless mode + Puzzle Storm.** Both in `VISION.md`; the store already supports an indefinite round count (Time Attack).

## Scores

### Game design — **5/10**

The core idea (target + grid + arithmetic path) is sound and proven. The current execution constrains it to a narrow straight-line puzzle, mis-teaches operator precedence, and gives the player no scaffolding to discover the rules. Learn mode's curriculum is the bright spot and earns the score above mediocre.

### UX — **5.5/10**

Visual design is clean, accessibility plumbing (keyboard, ARIA, motion-reduce) is genuinely good, and the home shell + Learn path layout punches above the project's weight. But operator buttons are too small, paths are invisible, wrong-answer feedback is useless, and the central rule (alternate tile/operator, straight lines only) is undocumented in-game. New-user onboarding will hemorrhage.

_Post-pass:_ larger operator targets, visible path, richer wrong-answer copy, onboarding tutorial, and on-card rule text improve this bucket materially; scores above remain the historical snapshot unless you re-score.

### Technical — **7/10**

Above-average architecture for a hobby project: clean separation of concerns, two thoughtful stores with persistence + migration, seeded RNG, testable utilities, lazy-loaded puzzle bundle, sensible routing. Lose points for: biased shuffle, the 1.1k-line `ButtonGameBoard`, duplicated constants (`MIN_NUMBER`/`MAX_NUMBER` in two files), dead state (`tile.selected`, unused `SUCCESS_DELAY`), and a "rating" field that pins to its floor for most of the bundle.

_Post-pass:_ biased target shuffle, dead `tile.selected`, unused-delay drift, and some timeout hygiene are improved; large-structure issues (`ButtonGameBoard` size, duplicate constants, rating floor, etc.) mostly remain.

## Top 5 things to implement first (repeat for emphasis)

_All five bullets were implemented in the post-review code pass (**Implementation status**). School BODMAS / true precedence in `calculator.ts` — not done._

1. **Display expressions with explicit parentheses as the player builds them, and tell them you evaluate left-to-right.** Removes the educational-harm risk and a major source of "why didn't my answer work?" confusion.
2. **Draw the path and preview legal next tiles.** Add a connecting stroke + soft outline on legal next picks. Eliminates ~80% of silent-rejection frustration.
3. **First-run tutorial + improved wrong-answer feedback** ("Your answer = 20. Target = 14. Off by +6"). Turns the game from "guess what I want" into "I understand the rules and I'm getting closer."
4. **Replace the broken shuffle and de-duplicate the curriculum** (`u2-l1` ≡ `u2-l2`; the `u3-l1` → `u3-l2` two-axis jump). Pure correctness wins.
5. **Cap and cost the hint, track personal bests, surface them on the Result page.** Smallest viable "skill is rewarded" intervention. Once PBs are visible, Time Attack and Quick Game actually _matter_.

> Fixing only these five moves the game design score from 5 → ~7 and the UX score from 5.5 → ~7.5 without touching the engine. The highest-leverage next move after that is **letting players pick any three connected tiles, not just a straight line** — delivers the "select 3 numbers" promise in the design doc and turns the puzzle into something an adult will play for longer than 60 seconds.
